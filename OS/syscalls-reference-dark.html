Linux System Calls Reference

What the CPU does on its own, what it must ask the kernel for, and which Java code triggers which syscall. Linux x86_64, HotSpot JVM.

Summary in Java terms

  • Pure computation never makes a syscall. Arithmetic, loops, method calls, new Object() (bump-pointer in a thread-local buffer), AtomicInteger.incrementAndGet(), and uncontended synchronized all run as plain CPU instructions.
  • Anything outside your process's memory needs the kernel: files, sockets, starting or waiting for threads/processes, sleeping, growing memory, signals.
  • Every Java I/O class sits on a handful of syscalls: openat → read/write → close for files, socket → bind → listen → accept for servers, epoll_* for NIO, Netty and virtual threads.
  • Syscalls are expensive compared to normal code (mode switch + validation), so the JDK batches them: BufferedReader, BufferedOutputStream, NIO buffers, transferTo (sendfile).
  • Exceptions are syscall errors: AccessDeniedException = EACCES, “Too many open files” = EMFILE, ConnectException: Connection refused = ECONNREFUSED, BindException: Address already in use = EADDRINUSE, NoSuchFileException = ENOENT.
  • The JVM makes many syscalls on its own before main() runs: mmap to reserve the heap, openat for jars and .so libraries, clone for GC/JIT threads, rt_sigaction for signal handlers.

What the CPU can do by itself vs what needs the kernel

A syscall is not a CPU feature. It is the kernel's API. The CPU's real capability is its instruction set (x86_64, ARM64). Some instructions run in user mode; others are privileged and only work in kernel mode. Syscalls exist so your program can get privileged work done safely.

User mode: your code runs these directly

  • Arithmetic and logic (add, multiply, shift, compare)
  • Load/store to memory already mapped to your process
  • Jumps, calls, returns (all of control flow)
  • Floating point and SIMD/vector (SSE, AVX, NEON); the JIT auto-vectorises loops, Java's Vector API targets these
  • Atomic instructions (lock cmpxchg, xadd): AtomicInteger, compareAndSet, VarHandle
  • Memory fences: what volatile compiles to
  • Reading the timestamp counter (rdtsc): basis of the fast vDSO clock
  • The syscall instruction itself: the doorway to the kernel

Kernel mode only: needs a syscall

  • Talking to devices (disk, NIC, GPU, keyboard) and handling their interrupts
  • Changing page tables: giving a process more memory, mapping files
  • Switching which thread runs on a CPU (scheduling, sleeping, waking)
  • Creating/destroying processes and threads
  • Enforcing permissions (UID/GID, capabilities)
  • Disabling interrupts, halting the CPU, configuring timers
  • Accessing another process's memory or sending it a signal
Key insight: synchronized and ReentrantLock first try a CPU atomic instruction (no syscall). Only when another thread holds the lock and waiting is needed do they call futex to sleep. That's why uncontended locks are cheap and contended ones are slow.

Virtual threads (Java 21+) do not call clone. They are scheduled by the JVM onto a few carrier (platform) threads. When a virtual thread blocks on a socket, the JVM parks it and registers the socket with epoll instead of blocking a kernel thread.

new Object() is not a syscall. The JVM got a big chunk of memory with mmap at startup and hands out objects from it itself. The OS only learns about memory when the heap grows or a page is touched for the first time (page fault, which is a kernel entry but not a syscall).

DNS lookup (InetAddress.getByName) has no dedicated syscall: glibc reads /etc/hosts and /etc/resolv.conf with openat/read, then sends a UDP query with socket/sendto/recvfrom.

This is how one thread serves 10,000 connections: instead of one blocked thread per socket (read sleeping), a single thread calls epoll_wait and only touches sockets that have data.

Signals

SyscallWhat it doesTriggered in Java by
rt_sigactionInstall a handler for a signalJVM startup: handles SIGTERM/SIGINT/SIGHUP (→ shutdown hooks), SIGQUIT (→ thread dump), SIGSEGV (→ NullPointerException trick)
rt_sigprocmaskBlock / unblock signals for a threadJVM thread setup
kill / tgkillSend a signal to a process / one specific threadProcess.destroy(); JVM uses tgkill internally

Runtime.addShutdownHook runs on SIGTERM/SIGINT (Ctrl+C, docker stop, Kubernetes pod shutdown) but never on SIGKILL (kill -9, OOM killer).

Isolation: the syscalls containers are built from

SyscallWhat it doesUsed by
clone CLONE_NEW*Start a process in new namespaces (PID, net, mount, UTS, IPC, user, cgroup)Docker/containerd/runc when starting a container

Limits (memory, CPU) are not syscalls: runtimes write to files under /sys/fs/cgroup. The JVM reads those files to size its heap (-XX:MaxRAMPercentage) and thread pools inside a container.

See it on your own machine

# Summary of every syscall a program makes
strace -c ls
strace -f -c java Sorter            # -f follows all JVM threads

# Watch specific families live
strace -f -e trace=openat,read,write java App
strace -f -e trace=network java App   # socket, connect, bind, accept...
strace -f -e trace=futex,clone java App

# Attach to a running JVM
strace -f -p <pid> -e trace=epoll_wait,read,write

# Full list of syscalls with numbers on your machine
ausyscall --dump          # from the auditd package
man 2 syscalls            # manual section 2 = syscalls
man 2 epoll_wait          # docs for one syscall
Manual sections: man 1 = commands, man 2 = syscalls (kernel), man 3 = C library functions (glibc). If man 2 xyz exists, xyz is a real syscall.
